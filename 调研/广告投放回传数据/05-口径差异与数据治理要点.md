# 口径差异与数据治理要点

本仓库 Demo 的核心矛盾是「同一指标各后台各说各话」。结合本次调研，建议把投放侧标准压成下面几条。

## 1. 禁止直接相加的字段

| 字段 | 为什么不能加 |
| --- | --- |
| 转化 | 优化事件不同：开口 ≠ 表单 ≠ 激活 ≠ Purchase；Google 还有 Conversions vs All conv. |
| ROAS / ROI | 归因窗口不同、是否含展示归因不同、收入是平台 GMV 还是你的实收不同 |
| 点击 | TikTok 有 all / destination；Google 视频用观看当互动；小红书互动可不经点击 |
| 花费 | 返点、赠款、税、币种、账户时区切日 |
| Reach | 平台内去重，跨平台重复人群无法去重 |

集团看板应展示 **「平台花费合计」**（仅花费相对可加，仍要统一币种与时区）和 **「店铺实收」**，用一方订单做利润，而不是把四个 ROAS 平均一下。

## 2. 建议的统一模型（逻辑层，不必一次接完 API）

```text
dim_ad_account     平台、账户ID、币种、时区、事业部、店铺
dim_campaign       平台侧计划/项目/Campaign
fact_ad_delivery_d 日期 × 账户 × 计划 × 创意：花费、展现、点击、平台转化
fact_click_id      gclid/ttclid/click_id 与会话、订单的映射（可选）
fact_lead          表单/私信线索明细（敏感）
fact_order         店铺订单（财务口径）
```

`fact_ad_delivery_d` 里平台转化只作「媒体自报」；经营转化以 `fact_order` / `fact_lead` 为准。

## 3. 时间与货币

| 项 | 做法 |
| --- | --- |
| 日切 | 每条投放事实保留 `platform_stat_date`（账户时区）和 `biz_date_cn`（北京时间） |
| 币种 | 保留原币 `cost_original` + `currency`，人民币用当日或财务约定汇率出 `cost_cny` |
| 转化时间 | Google 有「按点击日」和「按转化日」两列，必须标明 |

## 4. 归因窗口（写入指标字典的注释）

| 平台 | 常见默认（以后台设置为准） |
| --- | --- |
| 小红书私信 | 咨询/开口多按点击后 **24 小时** 计 |
| 巨量 | 按转化产品配置，点击窗口常见 7–30 天量级，需看事件管理 |
| TikTok | 常见 **7 日点击 + 1 日展示**，可改 1/7/14/28 日点击 |
| Google | 转化操作上配置回溯期；模型默认数据驱动 |

同一笔订单可能同时被 TikTok 和 Google 报成转化。治理上应标注「媒体归因」vs「最后点击一方归因」两套数。

## 5. 角色要的表不一样

| 角色 | 用哪层数据 |
| --- | --- |
| 投放 | 计划/素材、CTR、转化成本、视频 3s/6s、搜索词 |
| 运营 | 落地页停留、表单、开口到留资 |
| 财务 | 账户消耗对账单、返点、店铺实收、退款 |
| 老板 | 统一币种花费、一方订单利润、趋势；不看四个 ROAS 加总 |

## 6. 合规

线索手机号、监测链接里的设备号哈希、增强型转化上传的哈希邮箱，都按个人信息最小化：单独库、单独权限、不进默认看板下载。
