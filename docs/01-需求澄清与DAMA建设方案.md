# 海外拓客集团数据治理平台

## 需求澄清与 DAMA 建设方案（Demo 基线）

| 项 | 说明 |
| --- | --- |
| 文档用途 | 理清业务需求，作为 Demo 产品范围与面试表达的统一口径 |
| 企业画像 | 约 300 人集团，为海外店铺做拓客；主业是投广告 + 运营线上商店 |
| 数据体量 | 约数万条（订单/投放日汇总/客户级），非大数据量 |
| 核心矛盾 | 来源多、口径乱；同一指标在抖音、小红书、Google、店铺后台各说各话 |
| 两大交付 | ① 统一口径与数据字典 ② 分角色统计看板 |
| 方法框架 | DAMA-DMBOK2：车轮图 11 个知识领域 + 环境六边形；另将「大数据与数据科学」作为第 12 个工作视角 |

> 考证口径说明：DAMA 车轮图正式是 **11 个知识领域**，数据治理在中心、贯穿其余领域。业界常把 DMBOK2 专章「大数据与数据科学」并入讨论，凑成「12 个角度」。本文按此处理：先用车轮把治理体系说完整，再用第 12 视角约束「要不要上算法、上湖」。对 300 人、数万条数据的企业，这能避免把小数据问题做成大数据工程。

## 1. 业务理解：这家集团到底在干什么

### 1.1 价值链（先有业务链，才有数据链）

集团不是「纯技术公司」，也不是「纯货盘电商」。它的钱主要来自把流量变成海外店铺订单：

```text
选品/定价  →  广告获客  →  落地页/店铺转化  →  支付成交  →  履约物流  →  退款复购
                ↑                                      ↓
         抖音 / 小红书 / Google / Meta / TikTok     独立站 / 平台店 / OMS
```

两条主线必须同时看，不能做成两套互不相干的报表：

| 主线 | 日常在干什么 | 典型系统 | 他们真正关心的问题 |
| --- | --- | --- | --- |
| 广告投放 | 买流量、测素材、调出价、控成本 | 巨量引擎、小红书聚光、Google Ads、Meta、TikTok Ads | 花出去的钱有没有换来订单和利润 |
| 店铺运营 | 商品、详情页、活动、客服、库存、履约 | Shopify / Amazon / 独立站 / OMS / 支付 | 进店的人有没有买、买完有没有退、店是否赚钱 |

300 人规模通常意味着：多个事业部或多个店铺、多广告账户、多国家站点；报表靠 Excel 和各平台后台拼接；老板看到的数和投放看到的数对不上。

### 1.2 数据从哪来（来源多是既成事实）

Demo 与真实建设都按「先盘源、再统一」处理，不假设一次接完所有 API。

**投放侧（国内）**

- 抖音/巨量引擎：消耗、展示、点击、转化、素材、账户
- 小红书聚光：笔记/信息流投放、互动、线索或成交回传

**投放侧（海外）**

- Google Ads：搜索/购物/YouTube，归因窗口与转化定义和国内完全不同
- 常见还会有 Meta、TikTok Ads（即使当前口述未点名，架构上应预留）

**经营侧**

- 店铺后台：访客、加购、订单、GMV、退款
- 支付：PayPal / Stripe / 平台结算（币种、手续费）
- OMS/ERP：发货、库存、成本
- 表格：人工日报、对账表、线下调整

**管理侧**

- 组织：事业部、店铺、投放小组、人员
- 主数据雏形：店铺清单、广告账户清单、商品/SKU、国家、币种

### 1.3 真正的痛点（不是「没数据」，是「没同一套话」）

数万条数据用 Excel 也能算。集团要平台，是因为下面这些事 Excel 做不稳：

1. **同一个词，多个算法**：ROAS、转化、GMV、花费，各后台定义不同，直接相加会重复计算。
2. **时间和钱对不齐**：北京时间 vs 店铺当地时间 vs UTC；人民币 vs 美元 vs 当地币；含税/不含税。
3. **主体对不齐**：广告账户 ≠ 店铺 ≠ 商品 ≠ 客户；一个店铺多账户，一个 SKU 多站点。
4. **归因互相争功**：Meta 7 天点击+1 天浏览、Google 更长点击窗口、抖音转化口径又不同；各平台 ROAS 不能加总。
5. **角色要的不是同一张表**：老板看利润和趋势，投放看计划/素材，运营看漏斗和退款，财务看对账。

建设原则可以压成一句话：

**先立标准（什么叫对），再接数据（从哪来），再出看板（给谁看），全程可追溯（凭什么这么算）。**

## 2. 需求澄清：做什么、不做什么

### 2.1 建设目标（可验收）

| 目标 | 验收标准 |
| --- | --- |
| 统一核心口径 | 集团级「黄金指标」有唯一公式、唯一时间粒度、唯一币种规则、唯一数据源优先级 |
| 建成数据字典 | 业务人员能查：指标中文名、英文名、口径、来源系统、负责人、可用看板 |
| 分角色看板 | 老板 / 投放 / 运营 / 财务 至少各有一页，数字能对上字典 |
| 质量可见 | 缺数、重复、币种异常、花费与订单对不上时，有规则、有记录、有责任人 |
| 权限可用 | 按组织/店铺隔离；海外客户个人信息按最小必要展示 |

### 2.2 范围内 / 范围外

**范围内（Demo 必须能讲清楚、能点开看）**

- 指标与口径管理（数据字典 / 指标目录）
- 渠道与店铺等主数据、参考数据（国家、币种、平台编码）
- 多源接入后的标准层（即使 Demo 用模拟数据）
- 数据质量检核与问题清单
- 血缘：平台原始指标 → 标准指标 → 看板字段
- 四类角色看板

**明确不做（避免 Demo 做成「假大数据」）**

- Hadoop / 数据湖 / 实时百万级点击流
- 复杂多触点归因中台、用户级身份图谱（可规划，一期不做）
- 替代投放平台智能出价（平台 ROAS 仍给投放同学优化用）
- 一次性治理全部历史 Excel 和全部素材文件

### 2.3 成功标准（对老板一句话）

> 开会时不再争论「到底卖了多少、花了多少」；争论只允许发生在业务判断上，不允许发生在口径上。

## 3. 谁在用：角色、问题、看板

| 角色 | 典型问题 | 看板重点 | 权限 |
| --- | --- | --- | --- |
| 集团老板 / 管理层 | 这个月赚没赚钱？哪个国家/店铺该加预算？ | MER、毛利、花费、净销售额、趋势、异常 | 看全部汇总，可下钻事业部 |
| 事业部 / 店长 | 我的店转化掉了还是投放贵了？ | 店维度漏斗、花费、退款、TOP SKU | 只看自己店铺 |
| 投放优化师 | 哪条计划、哪个素材还能加？跨平台怎么比？ | 账户/计划/素材、平台原生指标 + 校准后经营指标 | 只看自己账户 |
| 店铺运营 | 流量来了为什么不成交？哪个品在退？ | 访客-加购-成交、详情页、库存、退款原因 | 只看自己店铺 |
| 财务 / 运营支持 | 平台花费和账单对得上吗？汇率怎么折？ | 花费对账、币种、手续费、退款、毛利 | 财务科目，脱敏客户信息 |
| 数据管理员 | 哪个指标改过？昨天哪路源断了？ | 字典、质量、血缘、任务状态 | 配置权 |

Demo 至少做出前四类页面，并在每张图旁标注「该指标来自字典哪一条」。这是治理平台和普通 BI 的差别。

## 4. 行业口径冲突清单（必须先治理的对象）

下列冲突是本项目的「业务资产」，数据字典要逐条写死，而不是只建一张空表。

### 4.1 花费（Spend）

- 平台后台消耗 vs 财务实付（优惠、授信、税、代理返点）
- 币种：账户币种 vs 人民币记账
- 时间：广告账户时区 vs 北京时间 vs 店铺时区

**集团建议口径（一期）**：经营看板的「广告花费」= 各平台消耗，按账户时区的自然日汇总，统一折算为人民币（用当日或当月固定汇率，字典里写死）；财务对账另设「实付花费」，两套数允许不同，但禁止混用。

### 4.2 转化 / 订单 / GMV / 销售额

- 广告平台「转化」= 像素/API 回传，含浏览归因，可跨平台重复
- 店铺「订单」= 已支付 / 已下单 / 已发货，三者差一截
- GMV 常含未支付、取消、运费；净销售额通常要扣退款、折扣、运费（需业务拍板）

**集团建议口径（一期）**：

| 指标 | 唯一事实来源 | 规则要点 |
| --- | --- | --- |
| 平台转化 | 各广告后台 | 只用于该渠道内部优化，禁止跨渠道加总 |
| 订单数 | 店铺/OMS 支付成功订单 | 取消、未支付不计 |
| GMV | 支付成功订单商品额 | 是否含运费在字典中单列 |
| 净销售额 | OMS | GMV − 退款 − 折扣（按财务确认） |
| 经营 ROAS | 净销售额 / 广告花费 | 跨渠道对比只用这一条 |
| MER | 广告花费 / 净销售额 | 给老板看整体投放效率，避开渠道争功 |

### 4.3 归因窗口

跨平台对比时，一期采用「点击归因、统一窗口（建议 7 日点击）」，浏览归因从对比表中剔除。平台原生 ROAS 仍可在投放看板单独展示，并标注「含平台默认归因，不可加总」。

### 4.4 客户与新客

- 广告「转化用户」≠ 店铺客户
- 新客：按邮箱/手机/平台买家 ID？按首单时间？按店铺还是集团？

**一期建议**：店铺内按买家 ID + 支付成功首单定义新客；集团级去重列入二期。

### 4.5 商品

同一商品在独立站、Amazon、广告素材里的 ID 不同。没有 SKU 映射，运营看板的「单品效果」是假的。SKU 映射是主数据，不是报表字段。

### 4.6 国家与站点

投放国家、收货国家、店铺站点、广告账户地区经常不一致。字典需规定：经营分析默认用**收货国家**，投放结构分析用**广告投放国家**，两套维度都保留。

## 5. 用 DAMA 框架怎么建、怎么干、怎么选工具

工作方法统一用环境六边形想问题，避免只谈工具：

| 环境要素 | 在本项目里问什么 |
| --- | --- |
| 目标与原则 | 这一域要保护哪条经营决策？ |
| 活动 | 计划 → 控制 → 开发 → 运营，具体做什么 |
| 交付物 | 制度、模型、字典、看板、质量报告 |
| 角色 | 谁拍板、谁录入、谁开发、谁值守 |
| 工具 | 300 人企业用什么；Demo 用什么 |
| 组织与文化 | 口径变更走审批，而不是投放同学私改 Excel |
| 技术 | 能否运维、能否演示、会不会过度设计 |

工具选择总原则：**体量小、语义重 → 选能把口径、血缘、质量、看板串起来的轻量栈，不选大数据套件。**

建议技术锚点（企业落地与 Demo 可同一套缩小版）：

| 层 | 企业落地（300 人） | 本 Demo |
| --- | --- | --- |
| 存储 | PostgreSQL | PostgreSQL（或 SQLite 便于携带） |
| 转换/测试/血缘 | dbt | dbt 或等价 SQL 分层 + 字典表 |
| 调度 | 日批即可（Airflow / 系统计划任务） | 手动导入或简单脚本 |
| 指标与元数据 | OpenMetadata / DataHub，或自建指标表 | **自建数据字典模块（Demo 核心）** |
| 质量 | dbt test + 规则表 | 质量检核页 |
| 看板 | Metabase / Superset | 自研看板（面试可讲解）或 Metabase |
| 主数据 | 独立主数据表 + 审批 | 店铺/账户/SKU/渠道维护页 |
| 不选 | Hadoop、ClickHouse 集群、Collibra 全套、实时数仓 | 同左 |

### 视角 1. 数据治理（车轮中心）

**对本企业意味着什么**

治理不是再买一套系统，而是规定：谁有权定义「净销售额」，口径改了谁审批，看板以哪套数为准。没有这一层，字典会变成无人维护的 Wiki，看板会迅速重新分裂成 Excel。

**工作如何开展**

1. **计划**：明确治理范围只覆盖投放+店铺经营数据，不治理全集团人事财务全量。
2. **组织**：300 人不设庞大委员会。建议「数据治理小组」：业务负责人（拍板口径）+ 数据管理员（维护字典）+ 开发（落地）+ 财务（对账口径一票否决）。
3. **制度**：指标准入、口径变更、数据问题升级。核心是 RACI：
   - 指标定义：业务 Owner 负责，数据管理员记录
   - 花费与收入：财务会签
   - 看板发布：未入字典的字段不准上线
4. **运营**：双周 30 分钟口径例会；月度质量报告给老板一页纸。

**工具**

制度用文档 + 平台里的「指标状态（草稿/生效/废弃）」即可。不必上 Collibra。

**Demo 要做到**

- 指标有状态、有 Owner、有生效日期
- 看板字段能跳到字典
- 能演示一次「口径变更」：改公式 → 旧版留痕 → 看板数字变化

---

### 视角 2. 数据架构

**对本企业意味着什么**

架构要回答：原始平台表、标准订单、黄金指标、看板之间怎么分层；以及「语义层」放在哪。对这家公司，**语义层（指标口径）就是架构核心**，不是集群拓扑。

**建议分层（经典数仓，足够）**

```text
源系统（广告API / 店铺 / Excel）
    → ODS  原样落地，保留平台原始字段和原始时区
    → DWD  清洗、统一时区与币种、统一主键
    → DIM  店铺、账户、SKU、渠道、日期、汇率
    → DWS  按日×店铺×渠道 汇总
    → ADS  面向看板的宽表
    → 指标字典 / 语义层   公式与口径（治理对象）
```

原则：

- ODS 不改口径，便于和后台对账
- 跨渠道对比只允许用 DWS/ADS 的经营口径
- 平台原生指标可并存，但打标「不可跨渠道加总」

**工具**：PostgreSQL Schema 分层即可。Demo 用 `ods / dwd / dim / dws / ads / gov` 六个 schema 就能把架构讲明白。

### 视角 3. 数据建模与设计

**对本企业意味着什么**

要能把「一次花费」和「一笔订单」在相同的店铺、日期、渠道、商品上对齐。没有共同维度，ROAS 是算不出来的。

**建议模型（星型，面向分析）**

事实：

- 投放事实（日 × 账户 × 计划 × 素材）：展示、点击、花费、平台转化
- 订单事实（订单行）：金额、币种、状态、客户、SKU、国家
- 退款事实、流量事实（若店铺能提供会话级；没有则用日汇总）

维度：

- 日期（含业务日、账户时区日）
- 组织 / 事业部 / 店铺
- 渠道 / 平台 / 广告账户 / 计划
- 商品 / SKU 映射
- 地理（投放国家、收货国家）
- 币种 / 汇率

**工作如何开展**：先画概念模型（业务对象：店铺、账户、订单、投放、商品、客户），再落逻辑模型，最后才建表。面试时能画出对象关系，比堆技术名词更像「做过治理」。

**Demo 要做到**：3～4 张核心事实 + 完整维度；字典中的每个黄金指标都能指出用了哪些表、哪些字段。

### 视角 4. 数据存储与操作

**对本企业意味着什么**

数万条、日批一次，备份、权限、导入失败重跑，比「弹性扩容」重要。

**工作如何开展**

- 日批：T+1 上午 10 点前出数（海外时区要在字典里写清截止点）
- 保留 ODS 至少 90 天便于对账
- 失败可重跑；禁止「半成功」写入 ADS
- Demo 提供「模拟拉取 / 重新计算」按钮即可

**工具**：PostgreSQL；Windows 上可用 Docker 或本地安装。不要引入分布式存储。

---

### 视角 5. 数据安全

**对本企业意味着什么**

海外店铺会碰到邮箱、电话、地址、支付相关信息，涉及 GDPR 与国内个保法。投放侧还有账户结构、花费，属于经营机密。300 人集团最常见的事故是：店长看到别的店的利润，或把客户清单导出到微信。

**一期控制**

- 行级权限：按店铺 / 事业部
- 列级：客户联系方式默认脱敏，财务/客服按需授权
- 角色：老板、店长、投放、运营、财务、管理员
- 审计：谁导出了客户或花费明细
- 源数据拉取遵守各广告平台 API 条款，Demo 用脱敏模拟数据

**工具**：数据库 RLS + 应用层角色。不必上专门的数据安全网关。

---

### 视角 6. 数据集成与互操作

**对本企业意味着什么**

这是「把数搬进来」的工程，但治理要求比管道更严：每条管道必须声明字段映射到字典的哪一项。

**工作如何开展**

1. 源系统清单（系统、Owner、更新频率、主键、时区、币种）
2. 映射表：源字段 → 标准字段（含单位换算）
3. 接入顺序：**先店铺订单 + 花费日汇总**（能算出 MER），再计划/素材，再客户
4. Excel 也是源系统，要登记，不能私自覆盖标准表

**工具**

- 生产：各平台官方 API + 小规模 Python；可用 dlt/Airbyte 减少连接器工作
- Demo：CSV/JSON 模拟三套源（抖音、小红书、Google）+ 一店铺订单，重点演示映射和冲突，而不是真去打广告 API

集成成功的标志不是「接了 20 个 API」，而是「Google 的 conversions 和抖音的转化，在标准层不会被加进同一个『订单数』」。

---

### 视角 7. 文档与内容管理

**对本企业意味着什么**

素材视频、笔记链接、投放 SOP、对账截图、合同，都是非结构化内容。一期不必做内容中台，但要能用 ID 把「素材」和投放效果连上，否则投放看板无法回答「哪类内容在赚钱」。

**一期范围**

- 素材主数据：素材 ID、平台、类型、关联计划、负责人
- 治理文档：口径说明书、质量规则、看板使用说明，作为平台内文档或 Git 文档
- 二期再考虑素材文件本身的存储与检索

**工具**：平台内 Markdown/帮助页 + 素材登记表。不选独立 ECM。

---

### 视角 8. 参考数据与主数据

**对本企业意味着什么**

口径冲突有一半其实是主数据没对齐：店铺没统一编码，渠道名称有「google / Google Ads / 谷歌 / SEM」四种写法。

**必须先做的主数据**

| 对象 | 为什么必须先做 | 黄金记录规则 |
| --- | --- | --- |
| 店铺 | 权限、经营汇总的根 | 一个经营主体一个店铺编码 |
| 广告账户 | 花费归属 | 账户绑定唯一店铺（多对一要显式维护） |
| 渠道/平台 | 跨源对比 | 封闭枚举：douyin / xiaohongshu / google / … |
| SKU / 商品 | 单品分析 | 集团 SKU ← 各平台商品 ID 映射 |
| 国家、币种 | 汇总 | ISO 标准码 |
| 汇率 | 人民币记账 | 日或月汇率表，来源写死 |
| 组织与人员 | 权限与 Owner | 与店铺、账户绑定 |

**工作如何开展**：先治理「店铺 + 渠道 + 账户」三件套，再做 SKU。客户主数据（跨店去重）放到二期。

**Demo 要做到**：可维护店铺/账户/渠道；故意准备脏数据（渠道别名）展示标准化前后对比。

---

### 视角 9. 数据仓库与商务智能

**对本企业意味着什么**

老板要的不是「有数仓」，而是开会能投屏的几张图。BI 必须消费标准层，禁止直连 ODS 做集团经营结论。

**看板信息架构（Demo 产品原型）**

1. **经营总览（老板）**：净销售额、广告花费、MER、毛利、环比；按事业部/国家/渠道；异常预警条
2. **投放工作台**：分平台原生指标 + 校准经营 ROAS；计划/素材排行；明确提示不可加总项
3. **店铺运营**：漏斗、客单、退款、TOP SKU、库存预警（有数据才做）
4. **财务对账**：花费平台数 vs 标准花费、汇率、未对账差异
5. **治理驾驶舱（数据管理员）**：字典覆盖率、质量评分、任务、待审批口径

**原则**：每张图标题用业务指标名，不用「图表 1」；图下注明时间范围、币种、口径版本。

**工具**：面试 Demo 用自研前端最能展示产品理解；若时间紧，Metabase 连 ADS 也可。二者都要挂字典链接。

---

### 视角 10. 元数据管理（数据字典是这里的主战场）

**对本企业意味着什么**

用户说的「建立数据字典」，在 DAMA 里主要落在元数据：业务元数据（口径）、技术元数据（表字段）、操作元数据（任务、质量）。

**字典最小必备字段**

- 指标编码、中文名、英文名、别名（各平台原名）
- 业务定义（人话）+ 计算公式（机器可执行或等价 SQL）
- 粒度（日/订单/计划）、单位、币种规则、时区规则
- 来源系统与源字段、标准表字段
- 可否跨渠道加总
- 业务 Owner、技术 Owner、生效状态、版本
- 使用该指标的看板

**工作如何开展**

1. 收集现有日报里出现的全部指标名词（预期 50+）
2. 合并同义词，挑出 12～20 个黄金指标优先入库
3. 其余指标标记「平台私有，仅供投放优化」
4. 新看板需求必须先立字典再开发

**工具**：自建 `gov_metric` 等表 + 前端字典页。OpenMetadata 适合以后，一期自建更利于 Demo 讲故事。

---

### 视角 11. 数据质量管理

**对本企业意味着什么**

质量不是「把表洗干净」，而是保证黄金指标适合拿来做预算决策。DAMA 常用维度都要落到具体规则：

| 质量维度 | 本业务规则示例 |
| --- | --- |
| 完整性 | 某账户某日花费缺失；订单无店铺编码 |
| 准确性 | 花费 < 0；汇率空却做了人民币折算 |
| 一致性 | 同一订单在 ODS 与 ADS 金额不一致 |
| 及时性 | T+1 10:00 前未出数 |
| 唯一性 | 订单号重复；账户绑定两个店铺且无说明 |
| 合理性 | 经营 ROAS 极端值；花费大增订单为零 |

**工作如何开展**：规则进表、每日跑、问题有工单状态（新/处理中/关闭）、月报给治理小组。先做阻断级规则（主键、必填、币种），再做预警级（ROAS 异常）。

**Demo 要做到**：质量看板 + 几条故意造的坏数据 + 规则说明引用字典。

---

### 视角 12. 大数据与数据科学（专章视角，不是车轮第 12 块）

**对本企业意味着什么**

数据量级撑不起「大数据平台」。数据科学可以有，但必须排在字典和看板之后，否则模型学的是错误口径。

**一期合理范围**

- 异常检测：花费突增、转化骤降（规则或简单统计即可）
- 素材/计划排序，不是深度模型
- 明确不承诺用户级归因模型、实时竞价、湖仓一体

**二期再考虑**

- 投放预算建议（在经营 ROAS 稳定之后）
- 退款风险、复购粗分群
- 若将来有点击流再评估仓储

面试时主动说清「为什么不上大数据」，反而体现 DAMA 判断力：技术选择服务业务问题，而不是服务热词。

## 6. 工作怎么开展：阶段节奏

300 人集团用「小步、可见、可回滚」。Demo 对应第 0 阶段，入职后可按同一路径放大。

### 第 0 阶段 · Demo（当前仓库要交付的）

- 模拟三源投放 + 一店铺订单
- 主数据：店铺、账户、渠道、SKU 映射、汇率
- 20 个以内黄金指标的字典
- 质量规则与治理驾驶舱
- 老板 / 投放 / 运营 三张看板（财务可简化）
- 文档与架构图齐全，能按 DAMA 讲解

### 第 1 阶段 · 30～60 天（入职后真建）

- 访谈老板、投放、运营、财务，收齐现有报表
- 冻结黄金指标 v1
- 接真实花费与订单（哪怕先 CSV）
- 出老板总览，先停掉互相矛盾的 Excel 总表

### 第 2 阶段 · 60～120 天

- 计划/素材级投放
- SKU 映射与运营看板
- 权限与对账
- 口径变更流程跑起来

### 第 3 阶段 · 半年左右

- 更多渠道、更多店铺
- 质量月报制度化
- 再评估是否需要 OpenMetadata、更细归因

**刻意不做的顺序**：先上全渠道实时大屏、先上 AI 归因、先上湖。那是在没有标准时放大噪音。

实现时优先做下面模块，已对齐第 0 阶段。未列入的不展开。

1. **登录与角色**：老板、投放、运营、财务、管理员

3. **主数据**：店铺、广告账户、渠道枚举、SKU 映射、汇率
4. **数据接入**：上传/载入模拟源数据，查看映射

## 8. 风险与表达注意

| 风险 | 应对 |
| --- | --- |
| 把治理做成纯 IT 项目 | 始终从老板决策和投放/运营吵架场景切入 |
| 工具清单像大型银行 | 反复强调数万条、语义复杂，用 Postgres + 字典 + 看板 |
| 用平台 ROAS 给老板加总 | 在字典和看板上用颜色/标记隔离 |
| 忽略海外合规 | 客户字段脱敏，Demo 数据全部虚构 |
| DAMA 背诵 11 域却落不到表 | 每个域都对应本平台一个可点功能或一张表 |
| 中文乱码 | 全部文档与代码注释使用 UTF-8 |

面试时可用的结构（约 3 分钟）：

1. 业务：海外拓客 = 投放 + 店铺，痛在口径不是痛在体量  
2. 方法：DAMA 车轮，治理居中；字典是元数据，看板是 DW/BI，对齐靠主数据  
3. 落地：先黄金指标和主数据，再分层数仓，再分角色看数  
4. 工具：Postgres + 指标字典 + 质量规则，不上大数据套件  
5. Demo：请看字典里的经营 ROAS 如何从三套源映射而来

## 9. 待业务确认的问题（Demo 先给默认值）

下列事项没有标准答案，需入职后由业务拍板。Demo 采用括号内默认值，并在字典中标注「待确认」。

1. 净销售额是否扣除运费、税费、支付手续费？（默认：扣退款和折扣，不扣运费）
2. 经营日报用北京时间还是店铺当地零点？（默认：北京时间自然日）
3. 人民币折算用当日汇率还是月平均？（默认：月平均记账汇率）
4. 代理返点是否冲减花费？（默认：经营花费不冲减，财务花费另计）
5. 是否包含 Meta / TikTok / Amazon 广告？（默认：架构预留，Demo 先做抖音、小红书、Google）
6. 店铺形态是独立站为主还是平台店为主？（默认：独立站订单模型）
7. 毛利的成本取采购成本还是含物流？（默认：商品成本，不含头程）

## 10. 一页结论

这家集团的数据治理平台，不是中台口号，而是把「多平台拓客」翻译成一套**可审计的经营语言**：

- **治理**定谁说了算  
- **主数据**定对象是不是同一个东西  
- **字典/元数据**定指标是不是同一句话  
- **集成与质量**定数能不能信  
- **数仓与看板**定不同角色能不能各看各的、又对得上  

数据只有数万条，所以平台应小、标准应硬、看板应分角色。Demo 只要把这三件事做透，就对齐了岗位要解决的真实问题。
